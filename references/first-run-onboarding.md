# 首次引导与候选人建档

首次引导的目标不是让用户填写一张长表，而是用最少问题建立一份经过用户确认、可持续更新的候选人事实库和求职配置。

## 何时读取

在以下情况读取本文件：

- 首次使用本 Skill；
- 没有可用候选人配置或证据库；
- 用户上传了新简历，且变化可能影响匹配或投递；
- 用户更换求职方向、城市、硬门槛或审批方式；
- 历史配置存在冲突或无法确认版本。

## 引导原则

- 先识别用户目标，再决定需要问多少问题；
- 先从简历和材料中提取，后追问缺失项，不让用户重复填写已经存在的信息；
- 每轮最多集中询问少量关键问题，允许用户跳过非必要项；
- 把“事实”“硬门槛”“偏好”“授权”分开确认；
- 未经确认的补充信息标记为 `UNVERIFIED`，不得写入对外材料；
- 引导可暂停和继续，不能因未完成全部可选项而阻止只读分析；
- 首次配置完成不等于授权投递。

## 首次引导状态流

```text
FIRST_RUN_CHECK
  ├─ 有可用配置 → LOAD_EXISTING_PROFILE
  │                 → DETECT_CHANGES
  │                 → CONFIRM_ONLY_CHANGED_ITEMS
  └─ 首次或配置不可用
       → SELECT_USER_GOAL
       → RESUME_INTAKE
       → EXTRACT_CANDIDATE_FACTS
       → CONFIRM_FACTS
       → COLLECT_REQUIRED_CONSTRAINTS
       → COLLECT_PREFERENCES_AND_EXCLUSIONS
       → BUILD_APPLICATION_ANSWER_BANK
       → SET_APPROVAL_POLICY
       → SELECT_SOURCE_AND_PLATFORM
       → CALIBRATE_WITH_SAMPLE_JOBS
       → CONFIRM_CONFIGURATION
       → SAVE_PROFILE
       → READY
```

保存中间状态：`NOT_STARTED`、`IN_PROGRESS`、`FACTS_PENDING`、`CONSTRAINTS_PENDING`、`PLATFORM_PENDING`、`CALIBRATION_PENDING`、`READY`。

## 第一步：识别用户目标

将目标归入最小必要模式：

- 分析用户给出的一个或多个JD；
- 自动搜索并建立候选池；
- 搜索、评分并生成待确认队列；
- 定制材料但暂不投递；
- 对用户确认的岗位或批次执行投递；
- 审计或继续已有求职活动。

只分析单个JD时，最低输入可以是简历与JD；不要强制完成与批量投递相关的全部配置。

## 第二步：接收和识别材料

优先请求当前正式简历。存在多份材料时，识别：

- 哪份是事实主版本；
- 哪些是岗位方向定制版；
- 哪些版本可对外发送；
- 是否存在作品集、项目说明、证书或推荐材料；
- 文件版本、更新时间和用户批准状态。

没有简历时，可以先建立空配置并指导上传；不得根据聊天印象重建完整履历。

## 第三步：提取候选人事实

从材料中提取并保留原始出处：

- 姓名与可公开联系方式；
- 工作、实习、项目和教育时间线；
- 雇主、职位、项目名称和工作性质；
- 实际职责、交付物、协作对象和使用场景；
- 技能、工具、方法、语言、证书和执照；
- 明确写出的量化成果；
- 作品集及其归属；
- 可能的日期冲突、表述冲突和证据缺口。

每条事实记录：

```text
fact_id
fact_type
fact_text
source_document
source_location
confidence
verification_status
sensitivity
allowed_uses
```

## 第四步：让用户确认事实

向用户展示结构化摘要，而不是重抄整份简历。明确询问：

- 哪些事实不准确；
- 哪些信息已经过期；
- 哪些内容可以用于分析但不能对外发送；
- 哪些成果属于团队而不是个人；
- 哪些数字、职责或技能需要进一步证明。

确认后的事实标记为 `VERIFIED`。用户未确认的新增内容保持 `UNVERIFIED`。事实冲突未解决时，不用冲突项定制材料。

## 第五步：只追问最低必要条件

自动搜索前至少确认：

- 目标岗位或岗位族；
- 地点及远程/混合办公要求；
- 法定或资格硬门槛；
- 明确排除的岗位、行业或公司；
- 本轮只分析、建立队列还是准备投递。

薪资、公司规模、融资阶段、出差、班次、入职时间等可按岗位和用户需要补充。用户说“不限制”时也要记录为明确选择，而不是缺失。

## 第六步：建立申请答案库

只保存用户确认过的常见申请答案：

- 当前与期望薪资；
- 到岗时间、通知期和离职状态；
- 工作授权、签证、国籍或安审资格；
- 是否接受出差、驻场、轮班或搬迁；
- 语言、证书和执照；
- 离职原因或求职动机的批准表述；
- 背景调查及其他声明。

每条答案包含适用范围、确认时间、敏感等级和有效期。申请时出现答案库之外的问题，必须进入 `NEEDS_USER`。

## 第七步：设置审批策略

让用户选择：

- 每个岗位单独确认；
- 对一份包含明确岗位标识的批次统一确认；
- 只允许搜索、评分和定制，不允许提交；
- 对有效期内的特定自动化任务授权明确平台、岗位范围、批次上限和停止条件。

无论选择哪种方式，岗位、材料版本或待发送文本发生实质变化后，相关旧批准失效。

## 第八步：小样本校准

首次批量搜索或投递前，默认用3—5个真实岗位进行校准：

- 展示推荐、人工复核和拒绝示例；
- 解释硬筛、证据映射和评分；
- 询问推荐范围是否过宽或过窄；
- 调整关键词、硬门槛、偏好、分数权重和阈值；
- 未完成校准时可以继续研究，但不进入大批量自动投递。

如果用户明确要求跳过校准，记录该决定；仍不得跳过岗位级人工确认和真实性要求。

## 建档完成标准

只有满足以下条件才标记 `READY`：

- 存在至少一份可用简历或已确认的事实库；
- 关键事实经过用户确认，冲突有明确状态；
- 本轮目标、最低硬门槛和排除项明确；
- 审批方式已选择；
- 自动搜索或投递需要的平台接入方式已经选择；
- 用户知道首次配置不等于授权任意投递。

## 回访用户与增量更新

回访时比较候选人配置、简历哈希/版本、求职目标和授权。只确认变化项：

- 新简历：重新提取差异并确认；
- 新方向：保留事实库，新增岗位配置和评分规则；
- 新平台：只执行平台接入检查；
- 新批次：重新确认岗位、材料和授权；
- 长期未使用：复核求职状态、答案库有效期和历史岗位状态。
